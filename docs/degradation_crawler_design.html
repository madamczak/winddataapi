1 The Problem

Wind turbine bearings, gearboxes, and generators degrade over years of operation. A classic early-warning signal is rising temperature under the same operating load. As bearing surfaces wear, friction increases; as gear oil degrades, heat transfer worsens; as generator insulation ages, copper losses grow. All of these produce excess heat.

⚠️ The naive approach fails: You cannot simply compare "nacelle temperature in June 2019 vs June 2022" — the nacelle temperature is dominated by ambient temperature and wind speed, not degradation. On a hot day at rated power, nacelle temp could be 10 °C higher than on a cold calm day, regardless of turbine condition.

The solution is to compare temperatures only when operating conditions are the same — same wind speed bin, same power output bin, same ambient temperature range — and track whether the temperature for those conditions drifts upward over time.

🌬️ Second-order effect — wind as a coolant (not in v1): Wind speed influences component temperatures in two opposing ways: higher wind means more mechanical load and faster rotation (more heat generated) but also stronger convective cooling of the nacelle shell and tower. The net effect is component-specific — generator bearings are mostly load-driven, while nacelle internal air temperature is strongly cooled by high winds even at rated power. In the initial version we account for wind speed only through the operating condition bin (which bundles load and wind together). A natural next step is to add wind speed as an explicit continuous covariate in a regression model (e.g. T_expected = f(power, ambient, wind)), which would remove the residual cooling effect and produce cleaner degradation residuals — especially useful for nacelle temperature. This is left as a v2 improvement.

2 Key Insight — Normalised Temperature

Define a temperature residual: the difference between the measured component temperature and an expected baseline temperature predicted purely from operating conditions.

ΔT = T_measured − T_baseline(wind_speed_bin, power_bin, ambient_bin) If ΔT drifts upward over months → degradation signal

The baseline T_baseline is built from the first 6–12 months of operation for each turbine (when it is assumed to be healthy), averaged within each operating condition bucket. Subsequent hours are compared against this baseline. A sustained positive drift (e.g. +3 °C over 6 months under equivalent conditions) is flagged.

✅ What this catches

  • Gradual bearing wear (front/rear main bearing, generator bearings)
  • Gear oil degradation — reduced heat transfer
  • Generator insulation aging — higher winding/stator temperatures
  • Cooling system blockage or fan degradation
  • Pitch bearing wear (via drive-train vibration → indirectly via temperature)

❌ What this does NOT catch

  • Sudden failures (use alarm codes for those)
  • Problems that don't generate heat (blade erosion, yaw misalignment)
  • Events that only last <1 hour (SCADA is 10-min averages)
  • Turbines with <6 months of healthy baseline data

6 Operating Condition Binning

Each hourly observation is assigned to a 3-dimensional bin. Only observations in the same bin are compared to the baseline — this normalises for ambient, wind, and load simultaneously.

🌬️ Wind Speed Bins

  • 3–5 m/s (cut-in)
  • 5–7 m/s (low)
  • 7–9 m/s (medium)
  • 9–11 m/s (high)
  • 11–13 m/s (near-rated)
  • 13+ m/s (rated / curtailed)

⚡ Power Output Bins

  • 0–200 kW (cut-in)
  • 200–800 kW (partial)
  • 800–1 500 kW (mid-load)
  • 1 500–2 000 kW (high)
  • 2 000+ kW (rated)

🌡️ Ambient Temp Bins

  • < 0 °C (freezing)
  • 0–10 °C (cold)
  • 10–20 °C (mild)
  • 20–30 °C (warm)
  • 30+ °C (hot)
💡 Minimum bin occupancy: A baseline bin must have ≥ 10 observations before it is used for comparison. Bins with fewer observations are skipped (not enough data to estimate a stable mean). This also means very rare operating conditions (e.g. extreme gusts at exactly cut-in power) are automatically excluded.

The bin key is a simple tuple string, e.g. "(9-11, 1500-2000, 10-20)". This keeps the baseline lookup O(1) with a dict. 

def get_bin(wind: float, power: float, ambient: float) -> str:
    wind_b = (
        "3-5"   if wind <  5  else
        "5-7"   if wind <  7  else
        "7-9"   if wind <  9  else
        "9-11"  if wind < 11  else
        "11-13" if wind < 13  else "13+"
    )
    power_b = (
        "0-200"     if power <  200  else
        "200-800"   if power <  800  else
        "800-1500"  if power < 1500  else
        "1500-2000" if power < 2000  else "2000+"
    )
    amb_b = (
        "<0"   if ambient <  0  else
        "0-10" if ambient < 10  else
        "10-20" if ambient < 20 else
        "20-30" if ambient < 30 else "30+"
    )
    return f"({wind_b}, {power_b}, {amb_b})"

7 Service Log Integration

The status dataset contains IEC-categorised events. These are critical for two reasons:

🔇 Masking

During and ±7 days after a maintenance event (IEC category M), temperatures are abnormal (parts disturbed, fresh grease, cooling circuits drained). These hours must be excluded from both baseline and residual calculations to avoid false signals.

🔄 Baseline Reset

After a major overhaul (bearing replacement, gearbox change), the turbine is effectively new again for that component. The baseline for affected temperature channels should be rebuilt from the 3 months following the overhaul.

The relevant IEC categories to watch for:

IEC CategoryMeaningAction
M — MaintenanceScheduled maintenance, lubricationMask ±7 days
R — RepairComponent repair or replacementMask ±14 days + reset baseline
F — Force majeureGrid, weather, external forced stopMask duration only
O — OperationalNormal stops, curtailmentNo masking needed
T — TestPerformance testsMask duration
 
def fetch_service_windows(
    session, api_base: str, farm: str, turbine: str
) -> list[tuple[date, date]]:
    """Return list of (start, end) date ranges to exclude for this turbine."""
    data = _get(session, f"{api_base}/wind-farms/{farm}/{turbine}/events")
    windows = []
    for evt in (data or {}).get("events", []):
        iec = evt.get("IEC category", "")
        if iec in ("M", "R", "T", "F"):
            t_start = date.fromisoformat(evt["Timestamp start"][:10])
            t_end   = date.fromisoformat(evt["Timestamp end"][:10])
            pad     = timedelta(days=14 if iec == "R" else 7)
            windows.append((t_start - pad, t_end + pad))
    return windows

def is_masked(d: date, windows: list) -> bool:
    return any(s <= d <= e for s, e in windows)

TEMP_COLS = [

    "Nacelle ambient temperature (°C)",

def build_baseline(api_base, farm, turbine, start_date, end_date, mask_windows, db_path):
    session = requests.Session()
    # bin_accum: bin_key → {col → [values]}
    bin_accum = defaultdict(lambda: defaultdict(list))

    d = start_date
    while d <= end_date:
        if is_masked(d, mask_windows):
            d += timedelta(days=1); continue

        for hour in range(24):
            data = fetch_hour_data(session, api_base, farm, turbine,
                                   d.isoformat(), hour,
                                   TEMP_COLS + COND_COLS)
            if not data or len(data["rows"]) < 4:
                continue
            wind    = _mean(_col_values(data, "Wind speed (m/s)"))
            power   = _mean(_col_values(data, "Power (kW)"))
            ambient = _mean(_col_values(data, "Nacelle ambient temperature (°C)"))
            if any(v is None for v in [wind, power, ambient]):
                continue
            b = get_bin(wind, power, ambient)
            for col in TEMP_COLS:
                vals = _col_values(data, col)
                if vals:
                    bin_accum[b][col].extend(vals)
        d += timedelta(days=1)

    # Compute means, save to SQLite
    conn = sqlite3.connect(db_path)
    conn.execute("""CREATE TABLE IF NOT EXISTS baseline
                    (farm TEXT, turbine TEXT, bin TEXT, col TEXT, mean REAL, n INT)""")
    for b, cols in bin_accum.items():
        for col, vals in cols.items():
            if len(vals) >= 10:
                conn.execute("INSERT OR REPLACE INTO baseline VALUES (?,?,?,?,?,?)",
                             (farm, turbine, b, col, sum(vals)/len(vals), len(vals)))
    conn.commit(); conn.close()

drift_detect.py — sliding window flag

from collections import deque

def detect_drift(residuals: list[dict], window_days=30,
                  warn_threshold=3.0, crit_threshold=5.0):
    """
    residuals: sorted list of {date, hour, col, delta_t}
    Returns list of alert dicts.
    """
    alerts = []
    from itertools import groupby
    # Group by column, then slide a 30-day window
    for col, rows in groupby(residuals, key=lambda r: r["col"]):
        rows = list(rows)
        for i, row in enumerate(rows):
            window = [r["delta_t"] for r in rows[max(0, i-72):i+1]]
            if len(window) < 12:  # need at least 12 comparable hours
                continue
            mean30 = sum(window) / len(window)
            if mean30 >= crit_threshold:
                alerts.append({"severity": "CRITICAL", "col": col,
                                "date": row["date"], "mean_delta": round(mean30, 2)})
            elif mean30 >= warn_threshold:
                alerts.append({"severity": "WARNING", "col": col,
                                "date": row["date"], "mean_delta": round(mean30, 2)})
    return alerts

12 Limitations & Gotchas

⚠️ Kelmarsh column inconsistency: Some temperature columns are absent or labelled differently across turbines (same issue seen with RPM columns in the existing crawler). Use column_candidates and validate values fall in physical ranges (e.g. bearing temps should be 20–100 °C; reject if mean is −999 or 0).
IssueImpactMitigation
Short baseline period Sparse bins → low confidence baselines Require ≥ 10 obs per bin; skip sparse bins
Sensor drift / recalibration Apparent ΔT even without degradation Compare against farm-average; flag outlier turbines only
Seasonal effects not fully captured by ambient bin Winter vs summer baseline mismatch Add month-of-year as a 4th binning dimension (4 seasons)
Missing service records Post-repair temperature drop looks like negative drift Flag sustained negative drift too — may indicate a recent repair
10-min SCADA averages smooth transients Early-stage failures with short-duration spikes are missed Watch Power, Standard deviation and vibration columns alongside temperature
API rate limits on Render free tier (cold starts) Slow crawl during baseline phase (years of data) Run baseline build once locally against local API, upload baseline.db
✅ Typical result to expect: On a 5-year dataset like Kelmarsh (2016–2021), a degrading generator bearing typically shows a sustained ΔT of +4–8 °C in the 3–6 months before an alarm is logged in the status data. This crawler would have flagged it 90–180 days before the reactive alarm — enough time to schedule a planned maintenance visit.

13 Deployment on Raspberry Pi & Bare-Metal / VM Hosts

13.1 Target Architecture

The crawler is designed to run on a small cluster of low-cost edge nodes. The reference setup is four Raspberry Pi 3B+ computers, but the same approach scales to any number of bare-metal servers or virtual machines.

Design principleRationale
Fully independent processes per node One Pi occasionally breaks or reboots. Each node runs its own cron/timer job and writes to its own local SQLite database. A failing node does not block the others — it simply resumes at the next scheduled run once it is back online.
No shared state between nodes Nodes do not need a shared filesystem or a distributed lock. Each node is assigned a disjoint subset of turbines (or a single farm) via an environment variable or a config file written during installation.
Auto-update before every crawl run Before executing the crawler, the runner script checks whether a newer commit exists on the configured GitHub branch. If one exists it pulls it and restarts the script automatically. No manual SSH is needed to deploy a code change — just git push from your laptop.
Horizontal scaling Adding capacity is a matter of running the same installer against a new IP. The node receives its turbine assignment as part of the installation step. Works equally well on bare-metal Linux boxes and on cloud/on-prem VMs.

13.3 Auto-Update Runner Script

crawler/run_with_update.sh — executed by systemd before every crawl. It compares the local commit to the upstream branch; if they differ it pulls the new code and re-executes itself so the new version is what actually runs. 

#!/usr/bin/env bash
# crawler/run_with_update.sh
# Checks GitHub for a newer version, pulls if available, then runs the crawler.
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
REPO_DIR="$(dirname "$SCRIPT_DIR")"
BRANCH="${REPO_BRANCH:-main}"
VENV="${REPO_DIR}/.venv/bin/python"
LOG="/var/log/windcrawler.log"

log() { echo "[$(date -Iseconds)] $*" | tee -a "$LOG"; }

# ── 1. Check for upstream changes ──────────────────────────────────────────
cd "$REPO_DIR"
git fetch origin "$BRANCH" --quiet

LOCAL_SHA=$(git rev-parse HEAD)
REMOTE_SHA=$(git rev-parse "origin/${BRANCH}")

if [ "$LOCAL_SHA" != "$REMOTE_SHA" ]; then
  log "New version detected (${LOCAL_SHA:0:7} → ${REMOTE_SHA:0:7}). Updating …"
  git reset --hard "origin/${BRANCH}"
  "${REPO_DIR}/.venv/bin/pip" install -q --upgrade -r "${REPO_DIR}/crawler/requirements.txt"
  log "Update complete. Re-executing with new code …"
  # Re-exec so the new script version is what runs
  exec bash "${BASH_SOURCE[0]}" "$@"
fi

log "Code is up-to-date (${LOCAL_SHA:0:7}). Starting crawler …"

# ── 2. Run the crawler ──────────────────────────────────────────────────────
# Pass the turbine filter from the environment (set by systemd EnvironmentFile)
"$VENV" "${REPO_DIR}/crawler/run_next_hour.py" \
  --turbines "${TURBINE_IDS:-ALL}" \
  2>&1 | tee -a "$LOG"

log "Crawler run finished."
StepWhat happens
git fetch origin Downloads remote refs without changing working tree — safe, fast, offline-harmless if it fails.
SHA comparison Compares local HEAD to origin/main. No network call needed after the fetch.
git reset --hard Applies the new code atomically; discards any local drift.
exec bash … Replaces the current process with a fresh execution of the (now updated) script. systemd sees no difference — the same PID tree continues.
No update path Script proceeds directly to the crawler call — zero overhead when nothing changed.

13.4 Scaling Beyond Four Raspberry Pis

The deployment model is stateless and identical across hardware classes:

  • More Raspberry Pis — run deploy_to_node.sh with a new IP and a different TURBINE_IDS slice. No changes to any existing node.
  • Bare-metal Linux servers — same script; swap pi user for your actual username via an environment variable (REMOTE_USER=ubuntu ./deploy_to_node.sh …).
  • Virtual machines (cloud or on-prem) — use SSH key-based auth instead of sshpass by passing -i ~/.ssh/id_rsa in the ssh commands; remove the sshpass wrapper. The rest of the script is identical.
  • Container / Kubernetes path — package the virtualenv and run_with_update.sh into a Docker image. The auto-update step is replaced by a standard image pull in a CronJob spec. Turbine assignment becomes a K8s ConfigMap or environment variable in the pod spec.
✅ Fault-tolerance summary: Because every node runs its own independent hourly timer and writes to its own local SQLite file, a node that crashes or is powered off simply misses those hours and resumes automatically on next boot. There is no leader-election, no distributed lock, and no single point of failure. If a Pi permanently breaks, re-run deploy_to_node.sh against the replacement hardware — the node will pull the latest code, receive its turbine assignment, and start crawling within two minutes.

14 Grafana Fleet Monitoring

The degradation crawler runs as a distributed, long-running background process across multiple nodes. Grafana is the operational hub: operators must be able to see — in a single dashboard — which machines are running, how long each run takes, which turbines have been processed, and when a node silently drops out. All observability flows through structured JSON logs → Grafana Loki → Grafana panels queried with LogQL. No separate metrics infrastructure (Prometheus, exporters) is needed.

14.1 Structured Logging with Machine Identity

Every log line must carry the node's identity so that a single Loki query can split results by machine. The node name is read from an environment variable set during installation, falling back to the OS hostname. A short run ID groups all log lines from one scheduled execution so you can see exactly how many turbines a single invocation processed — and at what speed.

Add the module below to the project and import it throughout the crawler:

def _now() -> str:

def log(level: str, event: str, **fields):

14.2 Heartbeat Protocol

Each crawl run emits a start heartbeat as its very first action and an end heartbeat as its last. The time between these two events is the run duration. Grafana alerts if no start heartbeat has been received from a machine within 90 minutes — meaning one full scheduled run was missed entirely, which is the dropout signal. 

from crawler.machine_logger import log, CODE_SHA

def run_crawler(turbines: list, farm: str):
    t_start = time.time()

    # ── Heartbeat: run started ───────────────────────────────────────
    log("INFO", "heartbeat_start",
        farm=farm, turbine_count=len(turbines), sha=CODE_SHA)

    errors = 0
    rows_total = 0

    for turbine in turbines:
        t0 = time.time()
        try:
            rows = crawl_turbine(farm, turbine)   # existing function
            rows_total += rows
            log("INFO", "turbine_done",
                farm=farm, turbine=turbine, rows=rows,
                duration_s=round(time.time() - t0, 1))
        except Exception as exc:
            errors += 1
            log("ERROR", "turbine_failed",
                farm=farm, turbine=turbine, error=str(exc))

    # ── Heartbeat: run finished ──────────────────────────────────────
    log("INFO", "heartbeat_end",
        farm=farm, turbines_processed=len(turbines),
        rows_total=rows_total, errors=errors,
        duration_s=round(time.time() - t_start, 1))

15 Result Classification — Evidence of Degradation vs. Healthy Operation

The crawler produces two completely separate output streams. A record in the DEGRADING bin means evidence of progressive temperature drift was found — and the record documents exactly how strong that evidence is. A record in the HEALTHY bin is not silence: it is an explicit, timestamped assertion that a component was assessed and found within normal bounds. Both are stored; both are displayed in Grafana; and the absence of a HEALTHY record for a turbine/component is itself an anomaly (it may mean the crawler has not run or the baseline is incomplete).

15.1 The Two Bins and Their Sub-Levels

✅ HEALTHY Bin

Emitted at the end of every assessment window where no drift was detected. Contains enough metadata to prove the assessment was based on real, representative data — not silence or missing observations.

  • HEALTHY — ΔT mean < 1.5 °C, slope ≈ 0, good coverage

A turbine that has not emitted a HEALTHY record in the last assessment period should appear as grey / unknown in the Grafana heatmap, not green.

⚠️ DEGRADING Bin

Emitted when the drift detector identifies a sustained temperature rise that cannot be explained by operating condition changes alone. Three sub-levels reflect certainty and urgency:

  • WATCH — ΔT mean 1.5–3 °C or slope 0.2–0.4 °C/mo. Monitor closely.
  • WARNING — ΔT mean 3–5 °C or slope > 0.4 °C/mo. Plan inspection.
  • CRITICAL — ΔT mean > 5 °C. Immediate review; likely within weeks of failure.

15.2 Evidence Criteria for Degradation

Each criterion is worth between 1 and 2 points. The evidence score (0–7) is computed for the assessment window and drives the severity classification. Single-criterion triggers always land at WATCH; multiple corroborated criteria escalate to WARNING or CRITICAL.

CriterionThresholdScoreRationale
Mean ΔT above WATCH Rolling 30-day mean ΔT > 1.5 °C +1 Temperature is persistently elevated above baseline; too early to alarm but worth watching
Mean ΔT above WARNING Rolling 30-day mean ΔT > 3.0 °C +2 Substantial sustained excess heat; historically correlates with 90-day failure window in Kelmarsh data
Positive slope sustained Linear slope of 90-day ΔT > 0.3 °C/month +1 Drift is not static noise — it is accelerating or at least monotonically increasing
Sigma exceedance Mean ΔT > 2σ above the baseline distribution for this bin +1 Mean is statistically unusual even after accounting for normal bin-level variance
Multi-sensor corroboration ≥ 1 other temperature sensor on the same component or drivetrain also has score ≥ 1 +2 Single-sensor drift is often sensor noise or miscalibration; two agreeing sensors is strong physical evidence
Pre-repair temporal match An IEC "R" (repair) event occurs within 90 days after this assessment date +1 (retrospective) Used during baseline validation only — confirms the alert was a true positive; not used in real-time scoring
💡 Score → severity mapping:
Score 0 → HEALTHY   Score 1–2 → WATCH   Score 3–4 → WARNING   Score 5+ → CRITICAL   — OR — mean ΔT alone can override: >3°C → WARNING, >5°C → CRITICAL regardless of score.

15.3 Evidence Criteria for Healthy Operation

A HEALTHY record is only emitted when all four conditions below are satisfied. This prevents the system from recording "healthy" for a turbine that simply has too few observations to say anything meaningful.

RequirementValueWhy it matters
Minimum observations ≥ 30 comparable hours in the assessment window Fewer than 30 comparable hours in the same operating bin means the mean estimate is unreliable; record is skipped
Mean ΔT bounded |mean ΔT| < 1.5 °C Mean must be close to baseline — both positive and large negative drift are suspicious
Slope bounded |slope| < 0.2 °C/month No meaningful trend in either direction; values are stationary around the baseline
Variance reasonable σ < 3 times the baseline bin σ Unusually high variance in a "healthy" window suggests intermittent faults or sensor noise; better to mark as unknown
⚠️ Large negative ΔT is also flagged: If the rolling mean ΔT drops below −2 °C relative to the baseline, a WATCH record is still written to the DEGRADING bin with a "direction": "negative" field. This typically indicates an unreported gearbox oil flush or bearing replacement that reset temperatures without an IEC "R" event — or a sensor failure. It is not safe to classify this as "healthy".

15.5 Classification Algorithm

Add classify_window() to crawler/degradation/drift_detect.py. Each call evaluates one turbine–component pair over an assessment window and returns a single AssessmentRecord that goes into either the HEALTHY or DEGRADING output file. 

from dataclasses import dataclass, asdict
from typing import Literal, Optional
from datetime import datetime, timezone

@dataclass
class AssessmentRecord:
    farm:             str
    turbine:          str
    component:        str
    bin:              Literal["HEALTHY", "DEGRADING"]
    severity:         Literal["HEALTHY", "WATCH", "WARNING", "CRITICAL"]
    period_start:     str
    period_end:       str
    mean_delta_t:     float    # rolling-window mean ΔT (°C)
    sigma:            float    # std-dev of ΔT in this window
    slope_per_month:  float    # linear slope (°C per month)
    observations:     int      # comparable-hours count
    evidence_score:   int      # 0–7
    corroborated_by:  list     # other components that also flagged
    direction:        str      # "positive" | "negative" | "stable"
    timestamp_utc:    str

def classify_window(
    residuals:        list[dict],   # [{date, delta_t}, …] sorted by date
    farm:             str,
    turbine:          str,
    component:        str,
    period_start:     str,
    period_end:       str,
    watch_thr:        float = 1.5,
    warn_thr:         float = 3.0,
    crit_thr:         float = 5.0,
    slope_watch:      float = 0.20,  # °C/month
    slope_warn:       float = 0.40,
    min_obs:          int   = 30,
    baseline_sigma:   float = None,  # if provided, enables σ-exceedance check
) -> Optional[AssessmentRecord]:
    """
    Classify one turbine/component window.
    Returns None if insufficient data — caller must treat that as UNKNOWN.
    """
    if len(residuals) < min_obs:
        return None

    deltas = [r["delta_t"] for r in residuals]
    n      = len(deltas)
    mean   = sum(deltas) / n
    sigma  = (sum((d - mean)**2 for d in deltas) / n) ** 0.5

    # Linear slope (per observation → converted to per month ≈ 720 obs)
    xs       = list(range(n))
    x_mean   = (n - 1) / 2
    denom    = sum((x - x_mean)**2 for x in xs) or 1e-9
    slope_mo = (sum((xs[i] - x_mean) * deltas[i] for i in range(n)) / denom) * 720

    # Score each evidence criterion
    score = 0
    if   mean >= crit_thr:   score += 2
    elif mean >= warn_thr:   score += 2
    elif mean >= watch_thr:  score += 1
    if   slope_mo >= slope_warn:  score += 1
    elif slope_mo >= slope_watch: score += 1
    if baseline_sigma and mean > 2 * baseline_sigma: score += 1
    # Multi-sensor corroboration added by caller: score += 2

    # Negative-direction anomaly check
    direction = "positive" if mean > 0 else ("negative" if mean < -2.0 else "stable")
    if direction == "negative":
        score = max(score, 1)  # at least WATCH for unexplained negative shift

    # Severity from score + hard override
    if   mean >= crit_thr or score >= 5: severity = "CRITICAL"
    elif mean >= warn_thr or score >= 3: severity = "WARNING"
    elif mean >= watch_thr or score >= 1: severity = "WATCH"
    else:                                    severity = "HEALTHY"

    return AssessmentRecord(
        farm=farm, turbine=turbine, component=component,
        bin="HEALTHY" if severity == "HEALTHY" else "DEGRADING",
        severity=severity,
        period_start=period_start, period_end=period_end,
        mean_delta_t=round(mean, 2), sigma=round(sigma, 2),
        slope_per_month=round(slope_mo, 3),
        observations=n, evidence_score=score,
        corroborated_by=[], direction=direction,
        timestamp_utc=datetime.now(timezone.utc).isoformat(timespec="seconds"),
    )

15.7 Multi-Sensor Corroboration

After all sensors on a turbine have been classified independently, run a second pass that links assessments by component group. When multiple sensors within the same physical subsystem show concurrent drift, the evidence score of each is boosted and the combined assessment is written to a separate corroborated_alerts.jsonl file — these are the highest-confidence records.

Component groupSensors involvedScore boost if ≥ 2 agree
Generator bearings Generator bearing front + rear temperature +2 — same bearing housing; both rising = physical confirmation
Generator windings Stator temperature 1 + Generator bearing front/rear +1 — different failure modes but share the same cooling path
Gearbox drivetrain Gear oil temperature + Front/rear main bearing temperature +1 — shared lubrication circuit; rise in either can heat the other
Nacelle ambient (reference only) Nacelle temperature 0 — used to cross-check; if nacelle temp is stable but component ΔT rises, the component signal is genuine 
def apply_corroboration(records: list[AssessmentRecord]) -> list[AssessmentRecord]:
    """
    Group records by turbine; for each component group where >= 2 sensors
    are at WATCH or above, boost the evidence_score of all members by +2
    and populate corroborated_by.
    """
    GROUPS = [
        ["Generator bearing front temperature (°C)",
         "Generator bearing rear temperature (°C)"],
        ["Gear oil temperature (°C)",
         "Front bearing temperature (°C)",
         "Rear bearing temperature (°C)"],
        ["Stator temperature 1 (°C)",
         "Generator bearing front temperature (°C)"],
    ]
    from itertools import groupby
    for turbine_key, grp in groupby(records, key=lambda r: (r.farm, r.turbine)):
        turbine_recs = list(grp)
        flagged = {r.component for r in turbine_recs if r.severity != "HEALTHY"}
        for group in GROUPS:
            active = [c for c in group if c in flagged]
            if len(active) >= 2:
                for rec in turbine_recs:
                    if rec.component in active:
                        rec.evidence_score += 2
                        rec.corroborated_by = [c for c in active if c != rec.component]
    return records

Modelled directly on the existing scripts/export_crawler_results.py. Run from the project root after a full crawl cycle or add it to the auto-runner script. 

"""
scripts/export_degradation_results.py
Reads healthy_records.jsonl and degrading_records.jsonl produced by the
degradation crawler and writes frontend/public/degradation_results.json
for consumption by the Vue frontend.

Usage:
    python scripts/export_degradation_results.py
"""
import json, pathlib, datetime
from collections import defaultdict

ROOT         = pathlib.Path(__file__).resolve().parent.parent
RESULTS_DIR  = ROOT / "crawler" / "degradation" / "results"
OUT_FILE     = ROOT / "frontend" / "public" / "degradation_results.json"

VIEW_META = {
    "critical": {
        "label":       "CRITICAL",
        "icon":        "🚨",
        "description": "Mean ΔT > 5°C or evidence score ≥ 5. Immediate inspection required.",
        "color":       "red",
    },
    "warning": {
        "label":       "WARNING",
        "icon":        "⚠️",
        "description": "Mean ΔT 3–5°C or evidence score ≥ 3. Plan inspection within 30 days.",
        "color":       "orange",
    },
    "watch": {
        "label":       "WATCH",
        "icon":        "👁️",
        "description": "Mean ΔT 1.5–3°C or evidence score ≥ 1. Monitor closely.",
        "color":       "yellow",
    },
    "healthy": {
        "label":       "HEALTHY",
        "icon":        "✅",
        "description": "Confirmed within normal bounds (most recent record per component).",
        "color":       "green",
    },
}

def load_jsonl(path: pathlib.Path) -> list:
    records = []
    try:
        for line in path.read_text(encoding="utf-8").splitlines():
            line = line.strip()
            if not line: continue
            try:
                obj = json.loads(line)
                if isinstance(obj, dict): records.append(obj)
            except json.JSONDecodeError:
                pass
    except FileNotFoundError:
        pass
    return records

def main():
    healthy   = load_jsonl(RESULTS_DIR / "healthy_records.jsonl")
    degrading = load_jsonl(RESULTS_DIR / "degrading_records.jsonl")

    # ── Build views (mirrors "patterns" in crawler_results.json) ─────────
    by_view = defaultdict(list)
    for rec in degrading:
        sev = rec.get("severity", "WATCH").lower()
        if sev in VIEW_META:
            by_view[sev].append(rec)

    # Keep only latest HEALTHY record per (farm, turbine, component)
    latest_healthy: dict = {}
    for rec in healthy:
        key = (rec.get("farm"), rec.get("turbine"), rec.get("component"))
        existing = latest_healthy.get(key)
        if not existing or rec.get("period_end", "") > existing.get("period_end", ""):
            latest_healthy[key] = rec
    by_view["healthy"] = sorted(
        latest_healthy.values(),
        key=lambda r: (r.get("farm",""), r.get("turbine",""), r.get("component",""))
    )

    # Sort degrading views: worst evidence first
    for sev in ("critical", "warning", "watch"):
        by_view[sev].sort(key=lambda r: (-r.get("evidence_score",0), -r.get("mean_delta_t",0)))

    views = {}
    for key, meta in VIEW_META.items():
        views[key] = {**meta, "count": len(by_view[key]), "records": by_view[key]}

    # ── Heatmap: newest assessment per (farm, turbine, component) ────────
    heatmap: dict = {}
    for rec in degrading + list(latest_healthy.values()):
        farm, turbine, comp = rec.get("farm",""), rec.get("turbine",""), rec.get("component","")
        heatmap.setdefault(farm, {}).setdefault(turbine, {})[comp] = {
            "severity":        rec.get("severity"),
            "bin":             rec.get("bin"),
            "mean_delta_t":    rec.get("mean_delta_t"),
            "evidence_score":  rec.get("evidence_score"),
            "slope_per_month": rec.get("slope_per_month"),
            "period_end":      rec.get("period_end"),
        }

    output = {
        "generated_at":      datetime.datetime.utcnow().strftime("%Y-%m-%dT%H:%M:%SZ"),
        "total_assessments": len(healthy) + len(degrading),
        "healthy_count":     len(healthy),
        "degrading_count":   len(degrading),
        "views":             views,
        "heatmap":           heatmap,
    }

    OUT_FILE.parent.mkdir(parents=True, exist_ok=True)
    OUT_FILE.write_text(json.dumps(output, indent=2), encoding="utf-8")
    print(f"✓ Written {output['total_assessments']} assessments "
          f"({output['degrading_count']} degrading, {output['healthy_count']} healthy) → {OUT_FILE}")

if __name__ == "__main__":
    main()

17.2 Dependency Files — Two Layers

Two files together enforce a fully reproducible environment:

📝 crawler/requirements.txt — intent

Human-readable. Lists only direct dependencies with exact versions. Edit this file when you want to add or upgrade a package. Never used for installation directly.

# Direct runtime dependencies
# Python target: 3.11.x
# All other imports are stdlib.

requests==2.32.3
# boto3==1.34.0  # S3/R2 (optional)

🔒 crawler/requirements.lock — enforcement

Auto-generated. Lists every package in the full transitive graph with exact versions. Used for installation on all nodes. Never edit by hand — regenerate when requirements.txt changes.

certifi==2024.8.30
charset-normalizer==3.4.0
idna==3.10
requests==2.32.3
urllib3==2.2.3
💡 Why not a single file? requirements.txt tells humans what the crawler directly depends on and why. requirements.lock tells pip exactly which bytes to install. Keeping them separate means a human can review one line in requirements.txt ("we upgraded requests to 2.32.3") without having to parse 50 lines of transitive noise.

# ── 1. Python version check ───────────────────────────────────────────────────
PY_VERSION=$(python3 -c "import sys; print(f'{sys.version_info.major}.{sys.version_info.minor}')")
PY_MAJOR=$(echo "$PY_VERSION" | cut -d. -f1)
PY_MINOR=$(echo "$PY_VERSION" | cut -d. -f2)
if [ "$PY_MAJOR" -lt 3 ] || { [ "$PY_MAJOR" -eq 3 ] && [ "$PY_MINOR" -lt 11 ]; }; then

python3 -m venv "$REPO_DIR/.venv"
"$REPO_DIR/.venv/bin/pip" install --quiet --upgrade pip

⚠️ --no-deps is intentional. Installing with --no-deps forces pip to install exactly and only the packages listed in the lock file — no surprise transitive upgrades. Because the lock file already contains the complete transitive graph, nothing is left out.

17.5 Runtime Environment Check — env_check.py

crawler/degradation/env_check.py is a small module that runs as a pre-flight check at the start of every scheduled crawl invocation. It verifies:

  • Python ≥ 3.11
  • Every package in REQUIRED_PACKAGES is installed at the exact pinned version

If any check fails it prints the mismatch to stderr and exits with code 1, which causes run_with_update.sh (§ 13.3) to abort before the crawler runs — so a broken install never silently produces garbage results. 

# crawler/degradation/env_check.py  (abbreviated)
import sys, importlib.metadata, argparse

REQUIRED_PACKAGES = {
    "requests":           "2.32.3",
    "certifi":            "2024.8.30",
    "charset-normalizer": "3.4.0",
    "idna":               "3.10",
    "urllib3":            "2.2.3",
}
REQUIRED_PYTHON = (3, 11)

def check(quiet=False) -> bool:
    errors = []
    if sys.version_info < REQUIRED_PYTHON:
        errors.append(f"  Python 3.11+ required, running {sys.version.split()[0]}")
    for pkg, ver in REQUIRED_PACKAGES.items():
        try:
            got = importlib.metadata.version(pkg)
            if got != ver: errors.append(f"  {pkg}: need {ver}, got {got}")
        except importlib.metadata.PackageNotFoundError:
            errors.append(f"  {pkg}: NOT INSTALLED")
    if errors:
        print("❌  Environment check FAILED:", file=sys.stderr)
        for e in errors: print(e, file=sys.stderr)
        print("Fix: pip install --no-deps -r crawler/requirements.lock", file=sys.stderr)
        return False
    if not quiet:
        print(f"✓  Environment OK  Python {sys.version.split()[0]}  requests {ver}")
    return True

17.6 How the Auto-Update Loop Enforces the Environment

Putting the version check together with the auto-update mechanism from § 13.3, the full sequence on every scheduled run is:

Step 1
🔍 git fetch
Compare local SHA to origin/main. Fast, no working-tree change.
Step 2
⬇️ git reset
If SHA differs: pull new code and run pip install --no-deps -r requirements.lock to sync packages.
Step 3
✅ env_check
Verify Python version and every package version. Abort with a clear error if anything is wrong.
Step 4
🕷️ Crawl
Only reached if steps 1–3 all pass. Guaranteed to run the intended code with the intended libraries.

Because code and lock file are committed together, a node that pulls a new commit will always install the packages that commit requires — atomically. There is no window where new code runs against old libraries.
